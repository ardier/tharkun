# Prepare a Zenodo release draft

Use **Actions → Prepare Zenodo draft → Run workflow** for a release you want to
propagate. It creates a new version in Tharkun's existing Zenodo series, reserves
a version DOI and uploads the runnable `tharkun.zip`. You review and publish it.

## One-time setup

Add a repository Actions secret named `ZENODO_TOKEN` under **Settings → Secrets
and variables → Actions**. Create the token in your own Zenodo account with
`deposit:write` and `deposit:actions`. Zenodo requires the latter scope for the
new-version action; this workflow never calls the publication endpoint.
Keep the token in the secret, never in a commit or workflow input.
The token's `deposit:actions` scope also permits publication; the helper rejects
all deposition actions except `newversion`, and publication remains your manual step.

## Each selected release

1. Increase the release's `major.minor.patch` version and build and validate the
   runnable ZIP using the release process. This workflow takes a finished archive;
   the public repository does not contain the bundle builder. Record its SHA256.
2. Push the corresponding public source tag. Create a GitHub release for that
   tag and attach the validated file named exactly `tharkun.zip`.
3. Run **Prepare Zenodo draft**, entering that tag and the validated SHA256.
4. Open the draft linked in the workflow summary. Review the files, version,
   description, title, creators, licence and copyright, then publish on Zenodo.
5. Use the newly published version DOI in the FM-Tools entry and rerun its CI.

The workflow verifies the downloaded SHA256 and compares every packaged
`tharkun` source file with the public tag, ignoring generated bytecode, before
contacting the authenticated Zenodo API. It inherits the existing record's
metadata, updates the version and publication date, and verifies Zenodo's file
checksum and size after upload.

Re-running the same workflow resumes its matching draft. A draft prepared
manually or for another release is left for manual review. If the same version
is already published, identical bytes are accepted without creating a version;
different bytes require a version bump. Published files are never replaced.
If a run stops immediately after creating a new version, before recording its
release marker, review that draft manually before retrying.

Run the isolated checks locally with
`python3 -m unittest discover -s tests -p test_zenodo_draft.py`. They mock Zenodo;
they do not require a token or create an upload.

The existing concept DOI is **10.5281/zenodo.15844050**. Each release gets its own
version DOI in that series. A reserved DOI becomes registered on publication.
The workflow does not change GitLab or mark a competition submission accepted.

Reference: [Zenodo REST API](https://developers.zenodo.org/#new-version).
